## Data and schema

Exactly seven persistence entities remain: User, Seller, Product, Category, TryOnSession, Cart, Order. Only nullable `items` JSONB columns are added to carts and orders. Existing records are preserved; a null legacy items field reads as an empty collection. No seeded products, accounts, categories, or charts are created at startup. Hibernate's existing `ddl-auto=update` performs the additive schema change when this backend starts; use reviewed migrations and backups in a deployed environment.

Cart JSON maps real product IDs to quantities. Checkout locks the current user and product rows, validates current stock, calculates prices on the server, reduces stock, stores item snapshots on Order, and clears the cart within one transaction. Existing historical orders without item snapshots keep their recorded totals and statuses. Order deletion is disabled to retain history. Payment, shipping, reviews, wishlist and invented analytics are absent from the customer flows.

## Endpoints

Public: `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/products`, `GET /api/products/{id}`, `GET /api/categories`, `GET /api/categories/{id}`.

Authenticated account endpoints:

| Method | Endpoint | Behavior |
| --- | --- | --- |
| GET | `/api/account/me` | Resolve session against the database |
| GET | `/api/account/cart` | Current user's quantities |
| POST | `/api/account/cart/{productId}` | Atomically add quantity |
| PUT | `/api/account/cart/{productId}` | Set quantity; zero removes |
| POST | `/api/account/checkout` | Place order from server cart |
| GET | `/api/account/seller` | Own seller profile |
| GET | `/api/account/products` | Own seller products |
| GET | `/api/orders` and `/{id}` | Own orders; admins can inspect all |
| POST | `/api/orders` | Compatibility endpoint; ignores client totals/identity and checks out server cart |
| GET, POST, PUT, DELETE | `/api/try-on-sessions` | Scoped session CRUD; creation derives user and AR type |

Seller/admin/super-admin product create/update/delete uses existing `/api/products` CRUD. Sellers cannot manage another seller's products; submitted seller IDs cannot override ownership. Product responses include real category and seller names. Missing product images are allowed, as are zero prices. AR types are validated and aliases normalized.

Admin/super-admin: existing `/api/users`, `/api/sellers`, `/api/categories` CRUD and `/api/orders/{id}/status`. Category cycles are rejected. Creating a seller profile for a CUSTOMER promotes that real account to SELLER. Duplicate seller profiles are rejected. Changes to administrator account details/deletion require SUPER_ADMIN; self-deletion is rejected.

Super-admin only: `PUT /api/users/{id}/role` with `{ "role": "CUSTOMER|SELLER|ADMIN|SUPER_ADMIN" }`. Self-role changes are rejected. No role is chosen during public registration. Bootstrap the first super admin by having the database owner promote a specific existing, registered account; the application does not fabricate one.

## UI and AR

Home/shop/search/category navigation uses backend products and categories. Empty collections remain empty, failures show errors and retry, and detail routes fetch the requested backend product. No localStorage database or offline fallback remains. JWTs use local/session storage according to the remember choice. Expired tokens clear the current session; 403 remains a real access error.

CUSTOMER: real profile, persistent cart, orders, session metadata. SELLER: real business profile and owned product create/edit/remove, stock, price, image URL, category and controlled AR type. ADMIN: real users/sellers/products/categories/orders. SUPER_ADMIN: the same management plus protected role assignment. Dashboard summaries use actual returned records.

`ProductImage` uses only `imageUrl`; missing/broken images show a CSS neutral state and loading is explicit. Put real images under `frontend/public` and save their root path (for example `/assets/my-product.png`), or use a supported HTTP(S) URL. Remote images used by AR must permit CORS so canvas capture/download works. Transparent front-facing accessory assets give the intended AR result.

`/try-on?productId=<numeric ID>` fetches that product and chooses the engine from arType: SHIRT/TSHIRT/CLOTHING -> shirt; EYEWEAR/SUNGLASSES -> eyewear; NECKLACE/JEWELRY -> necklace. No numeric ID controls behavior. Preview aliases are rejected and never shown. Known IDs 1, 2, 3 retain their SHIRT, EYEWEAR, EYEWEAR records and image URLs. A real necklace must be created before necklaces appear in the live collection.

Camera starts only on explicit user action; photo upload begins only after selection. No person photo is preloaded. Existing geometry, tracking hooks, smoothing and camera implementation are preserved. The known Modern Clear image retains its existing temple assembly; arbitrary eyewear uses its own image. The integrated pose worker remains pose-only, without optional segmentation-mask transfer. New assets may need fitting calibration; the existing black-shirt calibration is retained.

Session save persists real user/product/time/type and capture dimensions/source metadata. It does not upload or persist the private photo. Capture/download remains local, and session history identifies this clearly. Payment processing, persistent photo hosting, self-service password recovery, seller subscription billing, and seller order fulfillment are not implemented or advertised.
